## 一句话概述

用 5492 万条真实电商行为日志，完整走通「数据清洗 → MySQL 星型模型 → SQL 分析 → 统计建模 → API + 看板」链路，并给出可执行的复购运营结论。

## 简历精简版（3 条，适合一页简历）

- 基于天猫复购预测公开数据集（**5492 万条行为日志 / 42.4 万用户**），独立完成数据清洗、MySQL 星型模型设计与 19 项数据校验；按 `date_key` 分区使日期范围查询只扫必要分区，分区裁剪经 `EXPLAIN` 验证。
- 使用窗口函数与 CTE 完成日环比、7 日移动平均、帕累托累计、分区排名等 11 组 SQL 分析；逐条 `EXPLAIN` 审计 11 条查询并实测耗时，定位到「全期累计查询需 376 秒」的本质瓶颈，改为物化聚合表后接口响应从 **59 秒降至 0.004 秒**。
- 构建复购预测模型（ROC-AUC **0.6544**，5 折 × 3 轮重复验证 **0.6595 ± 0.0038**），并完成概率校准与业务换算：只触达分数前 10% 人群可命中 1,133 个真实复购用户，比随机挑选**多 654 个（2.37 倍）**。

## 简历展开版（5–6 条，适合项目经历栏）

- **数据处理**：清洗 5492 万行行为日志（分块读写以控制内存），对三个小文件做类型转换与缺失标记；用实测 ID 取值范围决定列类型（`MEDIUMINT`/`SMALLINT`），比全用 `INT` 节省约 440 MB。
- **数据库设计**：设计 1 事实 + 6 维度 + 2 样本表的星型模型，事实表不建代理主键、按 `date_key` 分区；批量导入采用「删索引 → 装载 → 一次性重建」，全量装载从预估 3 小时降至 **4.83 分钟**。
- **SQL 分析**：实现日环比（`LAG`）、7 日移动平均（窗口聚合）、帕累托累计占比（`SUM() OVER`）、`RANK`/`DENSE_RANK` 并列差异、商家内每日排名（`ROW_NUMBER`）等 11 组分析。
- **性能优化**：编写执行计划审计脚本，对 11 条查询逐条 `EXPLAIN` + 实测耗时，结论是瓶颈不在 SQL 写法而在「全期累计」口径本身；据此将 3 类聚合物化为表，接口从 **59 秒 / 376 秒降至 0.004 秒 / 0.04 秒**，并在物化脚本末尾加入一致性断言防止数据过期。
- **建模与评估**：构造 21 个特征（剔除 3 个零方差特征），对比 2 个基线 + 逻辑回归 / 随机森林 / 梯度提升；不只看 AUC，另做概率校准（Brier 0.05612、十分位偏差最大 0.0074）与特征共线性检查（VIF），并解释为什么前两名特征的重要性被摊薄。
- **工程化**：FastAPI 提供 12 个接口、Vue 3 看板（手写 SVG 图表，构建产物 85.6 kB）；**34 项测试**（18 单元 + 16 集成）+ GitHub Actions CI + ruff 全绿。

## 60 秒口述版

> 这个项目回答一个具体的运营问题：双十一当天买过我的人，之后还会不会回来。
>
> 数据是阿里云天池公开的 5492 万条行为日志、42.4 万用户。我把它清洗后装进 MySQL，设计了星型模型，事实表按日期分区——这一步踩过一个坑：一开始按月份分区，结果按日期的查询扫了全部 8 个分区，改成按 `date_key` 分区后才真正裁剪。
>
> 分析阶段我做了两件比较硬的事。第一，写了脚本把 11 条分析 SQL 逐条 `EXPLAIN` 并计时，发现最慢的一条要 376 秒，原因是「全期累计」类查询必须扫完全部数据，加索引救不了——所以我把结果物化成表，接口从 59 秒降到 4 毫秒。第二，模型不只看 AUC，还做了概率校准和业务换算：只触达前 10% 的人，能比随机多捞回 654 个真实复购用户。
>
> 最后我把结论、口径限制和不能算的指标都写在报告里，比如这份数据没有订单号和金额，所以不存在客单价和 GMV，我不会去编。

## 高频追问与答题要点

| 追问 | 答题要点（都有实测支撑） |
|---|---|
| AUC 只有 0.65，是不是太低了？ | 正例率 6.12%，特征窗口只到 1111 而复购发生在窗口之外；规则基线 ROC-AUC 只有 0.553，模型是 +0.1014。同时给出 PR-AUC 0.1196（比 ROC-AUC 更严格）和 5 折 × 3 轮重复验证 0.6595 ± 0.0038。 |
| 为什么不用准确率？ | 全预测为 0 就有 93.88% 准确率——这个数字是假信号，已写进报告。不平衡数据看 PR-AUC 与前 K% 命中率。 |
| 0.5 阈值下精确率是 0，模型没用吧？ | 不是模型问题：HGB 未做类别权重，概率整体压在 0.5 以下，一个正例都不报。按「预测正例率 = 目标触达比例」重新定阈值后 F1 是三个模型里最高（0.1665）。用 0.5 评判不平衡模型是常见错误。 |
| 老客复购率高，能说明先买一次有用吗？ | 不能。这是观察性对比：z=12.49、p≈8.9e-36 说明差异不是噪声，但两组非随机分配，存在混杂。要回答因果需要 A/B 实验。 |
| 59 秒变 0.004 秒，怎么做到的？ | 不是调 SQL。先审计发现瓶颈是「全期累计」必须扫全表；再把 3 类聚合物化成表（4 行 / 2 行 / 186 行），接口直接读结果。代价是数据更新必须重算，所以脚本末尾带一致性断言。 |
| 为什么没有客单价、转化率？ | 数据没有会话 ID、订单号、金额。有 9 项指标被明确列为「算不出来」并写进文档，替代口径一律不用。 |
| 1112 只有 46 行，你怎么处理的？ | 不删数据，打 `effective = 0` 标记，所有日均类指标按 185 天有效窗口计算。含它是 295,297，排除后是 296,893。 |
| 这个项目你一个人做的吗？ | 说明数据来源是公开比赛数据、模型与工程部分由你完成，如实回答即可。 |

## 不能说或不该写的

- **不要写竞赛排名或提交分数**——没有提交过。
- **不要写「提升复购率 XX%」**——离线模拟不是线上效果，真实增量需要 A/B 实验。
- **不要写转化率、客单价、GMV、ARPU**——数据里没有这些字段。
- **不要写「准确率 93.88%」当亮点**——那是全预测为 0 的假信号。
- **不要把「老客复购率更高」说成因果**。
- **不要说模型能预测单个用户**——它的定位是排序与名单筛选。

## 面试前建议准备的三个数字

1. **376 秒 → 0.04 秒**：说明你知道瓶颈在哪，也说明了代价（物化 + 一致性断言）。
2. **0.6544 / 0.6595 ± 0.0038**：说明你区分了单次评估与重复验证。
3. **多捞回 654 个复购用户**：说明你能把模型指标翻译成业务语言。
